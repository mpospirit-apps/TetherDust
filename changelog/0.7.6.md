# 0.7.6 — 2026-08-01

## Upgrade notes for admins
- Rebuild the `frontend` container to pick up the changes below; no
  migration needed.
- Restart the `tdmcp` and `backend` containers to pick up the
  `update_chart` prompt fix and the dashboard-generation changes below
  (all mount source live, but Python processes don't hot-reload
  module edits).
- Rebuild the `tdmcp` container (not just restart) to pick up the `mcp`
  dependency pin below — an already-built image has the broken `mcp`
  2.0.0 baked in and restarting alone won't fix it.

## Changed
- The Add/Edit Chart form's third step is now labeled "Layout and Position"
  instead of "Optional Configurations".
- The chart preview is no longer buried inside the sidebar's preview card
  with no heading — it's now its own numbered step ("04 Preview") in the
  same step sequence as Identity & Status / Configuration / Layout and
  Position, sitting above the AI editor in the sticky right column.
- The Database and Width dropdowns on the Add/Edit Chart form now use the
  app's `CustomSelect` (matching the styled dropdown used elsewhere, e.g.
  the Report form's Database/Schedule/Delivery fields) instead of a native
  `<select>`.
- The preview card's header now shows the row count / cache status message
  (e.g. "12 rows · just now") instead of a redundant "Preview" label, since
  the step heading above it already reads "04 Preview".
- Dropped the "Optional — " prefix from the Layout and Position step's
  description now that it reads as a normal step in the sequence rather
  than an optional aside.
- The Edit Dashboard page now uses the same numbered step layout (01
  Identity & Status / 02 Schedule and Access) as the Add Dashboard page,
  instead of a plain two-card layout with unlabeled `<h3>` headers
  ("Identity", "Refresh & access"). Both routes already shared the same
  `AdminDashboardFormPage` component; this removes the `isEdit` branch
  that gave them different layouts.
- The Add/Edit Dashboard form's second step is now labeled "Schedule and
  Access" instead of "Optional Configurations", and its description drops
  the "Optional — " prefix now that it reads as a normal step.
- The Refresh interval dropdown on the Add/Edit Dashboard form now uses
  the app's `CustomSelect` instead of a native `<select>`.
- The Style dropdown on the Generate Dashboard page now uses the app's
  `CustomSelect` instead of a native `<select>`.
- The Generate Dashboard page no longer lets you pick an agent — like
  Generate Documentation, it always runs on the active agent, so the
  "Agent" field and the `generate-options` endpoint's now-unused `agents`
  list are gone. The `generate` endpoint resolves the active
  `AgentConfiguration` itself instead of trusting a client-supplied
  `agent` id, and returns 400 if none is active (surfaced in the SPA as
  the same "No active agent configured" flash + disabled Generate button
  Generate Documentation already showed).
- The Generate Dashboard page now has a read-only "Prompt" step that
  shows the exact prompt generation will send, live-updating as the
  Style / custom instructions / source material change — matching the
  Prompt step on Generate Documentation. Backed by a new
  `POST /api/v1/admin/dashboards/generate-preview/` endpoint (mirrors
  `docsources`' `generate-preview`); `chartgen.start_generation`'s prompt
  construction was extracted into a pure `chartgen.build_generation_prompt`
  so both the preview and the real run build the identical prompt.
- The parts of that Prompt preview driven by the Configuration step
  (the Style template or Custom instructions text, and the "Available
  databases/documentation sources/codebases" lines from Source material)
  now render in accent lime, so it's clear which part of the prompt
  changes as those fields change. `generate-preview` now returns the
  prompt as `{text, is_configuration}` segments (via a new
  `chartgen.build_generation_prompt_segments`) instead of a single
  string, which `build_generation_prompt` now composes from.
- The Style dropdown on the Generate Dashboard page has a new "Custom"
  option. The "Custom instructions" field is no longer an always-visible
  optional override for any style — it now only appears (and is required)
  when "Custom" is selected, and is what's used verbatim as the prompt for
  that style. `chartgen.build_generation_prompt_segments` only honors
  `prompt_override` when `dashboard_type == "custom"`; the `generate`
  endpoint 400s if "Custom" is selected with no instructions.
- The Generate Dashboard page's "Style" dropdown is now "Instructions",
  defaults to "Custom" (so writing your own prompt is the primary path,
  not an opt-in), and lists the three canned styles (Overview, Time
  Series, Comparison) as the other options/presets. `generate-options`
  now returns `dashboard_types` with `"custom"` first, and both `generate`
  and `generate-preview` default `dashboard_type` to `"custom"` when
  unspecified.
- The custom-instructions textarea no longer renders as its own
  "Custom instructions" field below Source material — it's now nested
  directly under the Instructions dropdown, inside the same field, when
  "Custom" is selected.
- Refined the AI dashboard-generation prompts based on published BI/dashboard
  prompt-engineering guidance (chart-type-to-question mapping, KPI cards
  needing a comparison instead of a bare number, F-pattern layout
  ordering, ranking by value instead of alphabetically, capping pie
  charts at 5 categories). The three preset styles (Overview, Time
  Series, Comparison) in `DASHBOARD_TEMPLATES`
  (`engine/prompts/dashboards.py`) got more specific guidance for their
  focus; a new "Chart design guidelines" section was added to the shared
  tool instruction in `chartgen.build_generation_prompt_segments` so it
  applies to every generation, including "Custom" instructions.
- The dashboard-generation prompt and the `add_chart` tool definition now
  tell the agent to color a chart's sub-elements — each bar, line, or
  slice — distinctly via `theme.colors` (`d3.scaleOrdinal().range(theme.colors)`)
  instead of one flat color for the whole series, so multi-category charts
  read as visually varied instead of monotone. Single-value KPI cards are
  explicitly carved out (kept in `theme.accent`/`theme.colors[0]`, not
  rotated) since they have nothing to alternate and rotating them
  chart-to-chart just looked inconsistent card to card — the first version
  of this guidance alternated the *chart's* color rather than its
  sub-elements, which produced exactly that. Added to
  `chartgen.build_generation_prompt_segments`'s "Chart design guidelines"
  and `tdmcp/tools/add_chart.py`'s `d3_code` guidance.
- Chart color guidance now also covers using color *meaningfully*: for
  values with a clear direction (a KPI's trend arrow, a %-change badge,
  bars/cells crossing a good/bad threshold), the agent is told to color
  by direction — `theme.colors[2]` (lime) for increase/positive/good,
  `theme.colors[0]` (red) for decrease/negative/bad — matching `theme.colors`'
  fixed order in `frontend/src/charts/render.ts`'s `buildTheme`
  (`[red, cyan, lime, orange, pink]`), rather than only using color for
  categorical variety. Explicitly scoped to genuinely directional
  values, not decoration, and doesn't override a KPI card's own base
  color. Added to `chartgen.build_generation_prompt_segments`, and to
  both `add_chart.py` and `update_chart.py`'s `d3_code` guidance (the
  latter since re-coloring an existing chart by direction is a plausible
  edit request on its own).

## Fixed
- `tdmcp` failed to start (`ModuleNotFoundError: No module named
  'mcp.server.fastmcp'`), taking every service that depends on it down
  too. The `mcp` PyPI package released a breaking `2.0.0` that removed
  `mcp.server.fastmcp` (rewritten around a new `MCPServer`/`runner` API);
  `pyproject.toml`'s `mcp>=1.6.0` had no upper bound, and `tdmcp`'s
  Dockerfile does a plain `pip install` at build time rather than
  installing from `uv.lock`, so a rebuild picked up 2.0.0 straight from
  PyPI. Pinned to `mcp>=1.6.0,<2.0.0` in `pyproject.toml` (and mirrored
  the same cap in `containers/local_mcp/Dockerfile`'s inline `mcp` pin,
  which had the same unbounded gap even though it only uses unaffected
  client-side APIs) and regenerated `uv.lock`.
- The Preview and AI editor cards on the Add/Edit Chart page (`.chart-preview-card`,
  `.chart-aichat-card`) now use the same translucent, blurred glass background
  as every other `.card` in the app instead of a flat opaque `var(--surface)`
  fill, so they read as part of the same design system as the surrounding
  form cards in both light and dark theme.
- Sending a message in the Edit Chart page's AI editor no longer just
  reloads the page and drops the message. The AI editor rendered its own
  `<form>` inside the page's outer `<form id="chart-form">` — nested
  `<form>` elements are invalid HTML, and the browser could fall back to a
  native full-page submission instead of ever invoking the AI editor's own
  submit handler. It's now a plain `<div>` that sends on button click or
  Enter, so it can't be mistaken for the outer form's submit.
- The chart AI editor no longer silently ignores a literal color request
  (e.g. "make the line yellow") while still reporting a plain success.
  `update_chart` requires all d3 colors to come from the theme palette
  (by design — charts must stay consistent across light/dark), so a named
  color like "yellow" was never actually applied; the agent just kept the
  existing theme color but didn't say so. `tdmcp/tools/update_chart.py`
  and `engine/prompts/charts.py` (the chart-edit turn prompt) now require
  the agent to substitute the closest theme color and say so explicitly
  in its reply, instead of reporting an unqualified success.
- On the Add/Edit Dashboard form, the "Refresh interval" field that
  appears once "Auto refresh" is toggled on used to sit crowded directly
  against the toggle's own label/description, since `.toggle-row` (unlike
  `.form-group`) carries no bottom margin — reading as if it belonged to
  the toggle rather than being its own field. Added a
  `.toggle-row + .form-group` spacing rule so any field conditionally
  shown right after a `ToggleField` gets proper separation.
