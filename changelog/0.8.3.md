# 0.8.3 — 2026-09-13

## Upgrade notes for admins
- Run the migration: `docker compose exec backend python manage.py migrate`.
  It resets any role whose **Max Row Limit** is below 1 back to the default of
  100, and removes staff access from non-superusers whose role is an
  **inactive** admin role.
- Rebuild the frontend image:
  `docker compose build frontend && docker compose up -d frontend`.
- Staff users who edit roles now need **Can manage users** on their role (or to
  be a superuser). Everyone else on the console can still open and read roles,
  but no longer edit them. Grant the flag to your role admins before upgrading.
- Roles you had switched off with **Is active** now actually take effect: their
  users lose chat, data and page access on their next request or chat
  connection. Check Console → Roles for inactive roles that still have users.

## Changed
- Console → Roles is read-only for staff without **Can manage users**: no Add
  or Delete buttons, **Edit** becomes **View**, and the role page shows a
  disabled form with a note explaining why. `/api/v1/auth/me/` now returns a
  `can_manage_users` flag so the SPA can tell.
- The user form's role picker labels inactive roles
  `(inactive — grants nothing)`.

## Fixed
- A staff user could give themselves user management. The roles API only
  required staff, while the users API required **Can manage users** — so a staff
  user without it could tick the flag on their own role and then manage users,
  or flip any role to admin and make every user holding it staff. Creating,
  editing and deleting roles now needs the same `CanManageUsers` permission as
  the users API. Reading roles (and the grants list) stays open to all staff,
  since the dashboard, report and tether forms pick from them.
- **Is active** on a role did nothing. `Role.is_active` was only read for the
  console overview's role count, so an inactive role still granted chat, tools,
  databases, doc sources, codebases, prompts, MCP servers, reports, dashboards
  and tethers, and an inactive admin role still made its users staff.
  `PermissionService` now treats an inactive role exactly like no role, the
  role and user admin APIs only grant staff for an *active* admin role
  (`Role.grants_admin`), and **Can manage users** only counts on an active role.
- **Max Row Limit** accepted 0 and negative numbers. The value goes straight
  into the query's `LIMIT`, so 0 returned no rows and a negative limit failed
  every query for that role. The field now has a minimum of 1, in the API and
  the form.
- Clearing **Max Row Limit** in the role form sent `null` and came back as a
  raw `max_row_limit: This field may not be null.` error. The field is now
  required, so the browser asks for a value before submitting, and the
  frontend `Role` type no longer claims the limit can be `null`.

## Added
- Tests for the role write gate (including the self-grant path), the row-limit
  floor, inactive roles in `PermissionService`, the role → staff sync on
  deactivation and assignment, and `can_manage_users` on `/auth/me`.
