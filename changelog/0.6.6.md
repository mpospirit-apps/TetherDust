# 0.6.6 — 2026-07-20

## Upgrade notes for admins
- None.

## Changed
- The MCP Servers admin list's **+ Add Server** button (header and empty
  state) and the Getting Started wizard's **Add Server** step action are now
  labeled **Add MCP Server**, matching the page's own "MCP Servers" naming.
- Add MCP Server's step-1 connection picker ("Choose how it connects") now
  groups its two options into labeled **Remote** and **Local** sections using
  `choice-section`/`choice-list--grid`, matching the grouped option pickers
  on Add Codebase (Remote/Local providers) and Add Database Connection
  (engine groups) — instead of a single flat, ungrouped `choice-list`.
- The MCP Servers admin list dropped its **Type** column. Each server's type
  (Built-in / Remote / Local) is now shown as an icon (`fa-server` /
  `fa-globe` / `fa-terminal`) before its name via the shared `db-name-cell`
  layout, matching the icon-before-name pattern on the Databases and
  Codebases admin lists.
- The MCP server detail page's **Tools** list is no longer a table — tools
  now render as the same option cards used on Add Documentation/Add Codebase
  (icon, name, internal tool name, description), grouped into a
  `choice-section` per category (Charts, Codebases, Docs, Querying, Reports,
  Tethers) instead of a flat table with a Category badge column. Added a
  `.choice-card--static` CSS modifier so these read-only cards keep the same
  look without the hover/pointer affordance of the clickable option pickers
  they're modeled on. Initially carried over the table's per-tool ON/OFF
  badge, but removed it — every tool listed here is always enabled (there's
  no per-server tool toggle), so the badge never conveyed anything.
- The Tethers tool category's card icon is now `fa-diagram-project`, matching
  the Tethers nav tab's own icon (it was `fa-link`). Every tool category
  icon is now colored to match its counterpart nav tab accent (Docs=lime,
  Charts=red like the Dashboards tab, Reports=orange, Tethers=pink);
  Querying and Codebases have no nav-tab counterpart, so they keep the
  app-wide default icon color (cyan, also the Chat tab's accent).

- Custom (non-built-in) MCP servers no longer have a view page. The MCP
  Servers admin list's row action for a custom server is now **Edit**/
  **Delete** (no **View**) — built-in servers keep **View** only, since they
  still can't be edited. Navigating directly to a custom server's old detail
  URL now redirects to its edit page. The **Tools** and **Prompts** sections
  — which only ever had content for the built-in server, since custom
  servers have no locally-introspectable tools and prompts are keyed to the
  built-in server in practice — are gone from that flow entirely; the detail
  page (`MCPServerDetailPage.tsx`) is now built-in-only and keeps just Tools
  + Prompts.
- The custom-server **Test connection** button and its result now live on
  the **Edit** page instead of the removed view page, as a fourth
  "Test Connection" wizard step alongside Identity & Status, Configuration,
  and Optional Configurations.
- Edit MCP Server now uses the same step-by-step layout as Add MCP Server —
  `wizard-section`/`WizardSectionHeading` cards in a `form-split-col`,
  instead of two plain `form-split` cards labeled "Identity"/"Connection".
  Create and Edit now share one render, gated on the same `kind` state
  ("remote" or "local"): only the relevant Configuration/Optional fields
  ever show, replacing the old always-both-fields edit form and its
  "Set a URL … or a command … — not both" caveat. Edit derives the initial
  kind from the saved server and adds a **Type** selector (Configuration
  step) to change it — like Add Codebase's edit-only Provider selector —
  instead of a Create-only picker screen. `onSubmit` now sends only the
  active kind's fields (`url`/`headers` for remote, `command`/`args`/
  `command_env` for local), so switching kind can no longer leak the other
  type's stale form state into the save request.
- Add/Edit MCP Server's title now carries a `title-icon-tag` icon
  (`fa-globe`/`fa-terminal` by kind) before the "Edit …"/kind-label text,
  matching Add/Edit Database Connection's `EngineIconGlyph`-before-title
  layout. Edit's **Test connection** button moved out of its own wizard
  step and into the page header's `form-actions`, between **Cancel** and
  **Save Changes** — also matching Database Connection's Cancel/Test/Save
  button order — with the probe result rendered as a card directly under
  the header instead of at the bottom of the form.
- The Add/Edit MCP Server title icon is now colored `var(--c-cyan)` (the
  app's default accent, used elsewhere for sections with no nav-tab
  counterpart — see Tools category icons in `changelog/0.6.6.md` above).
  The Test connection result (`ProbeReport`) is now a `flash`
  `flash-success`/`flash-error` box (red/green, matching Database
  Connection's Cancel/Test/Save result) instead of a neutral card with a
  small badge chip. Extracted `ProbeReport` into a shared
  `admin/components/mcpProbe.tsx` so the MCP Servers list (below) can reuse
  it.
- The MCP Servers admin list's Actions column gained an inline **Test**
  button for custom (non-built-in) servers, between Edit and Delete — the
  row action order now matches Database Connections' Test/Edit/Delete.
  Testing renders the shared `ProbeReport` in a full-width row below
  (`.db-test-result-cell`), exactly like Database Connections' inline row
  test. Refactored each row into its own `MCPServerRow` component so the
  test mutation/result state stays per-row, mirroring `DatabaseRow` on
  `DatabasesPage.tsx`.
- `MCPServerDetailPage.tsx` is renamed to `MCPServerToolsPage.tsx` (same
  route, `/admin/mcp-servers/:id`) and its title now carries a
  `title-icon-tag fa-server` icon (colored `var(--c-cyan)`) before the
  server name, matching Add/Edit MCP Server's kind icon and Add/Edit
  Database Connection's engine icon, and now reads "{name} MCP Server"
  (e.g. "Built-in MCP Server") instead of just the bare server name. Tools
  stays above Prompts on this one page, same as before. The MCP Servers
  admin list's built-in row action is now labeled **Tools and Prompts**
  (`fa-wrench`, was **View**). Removed the card showing Type/URL/Command/
  Status underneath the header — Type and Status were the only fields that
  ever rendered there (the built-in server has no URL or command).
- The built-in MCP server's tool rows (`tool_name`/`display_name`/`description`)
  used to come from `BUILTIN_TOOLS`, a hand-typed list in
  `backend/engine/builtin_mcp.py` duplicating each tool's real name and a
  paraphrased description — free to drift from `tdmcp/tools/*.py`, and easy to
  forget entirely when adding a new tool (the tool would work but never show
  up in the admin UI or be assignable via `Role.allowed_tools`). Removed
  `BUILTIN_TOOLS`. `tdmcp/tools/__init__.py` now exposes `iter_tool_handlers()`
  (the same handler list `register_tools()` feeds to FastMCP, extracted out
  as the single source of truth for "what tools exist"), and
  `ensure_builtin_mcp()` derives `tool_name`/`display_name`/`description`
  straight from each handler's real name and docstring — the exact text
  FastMCP sends the agent — via a new `iter_builtin_tools()`. `category` has
  no equivalent in tdmcp (it's a TetherDust admin-UI grouping concept), so it
  keeps a small `TOOL_CATEGORIES` map; anything missing from it falls back to
  "Other" instead of erroring. Seeding switched from create-only
  (`get_or_create`) to `update_or_create` for the derived fields, so an
  existing install's rows now pick up a tdmcp docstring change on the next
  deploy instead of staying stuck with whatever was seeded originally;
  `is_enabled` is still only ever set on first create. Updated
  `tests/tdmcp/test_builtin_mcp_seed.py` for the renamed API (its assertion —
  seeded tool names match what's actually registered — is now true by
  construction, since both read from `iter_tool_handlers()`, but it still
  guards against a future refactor splitting them apart again). Also added a
  regression test covering the new pruning behavior below.
- `ensure_builtin_mcp()` now deletes any built-in `ToolConfiguration` row
  whose `tool_name` is no longer in `iter_builtin_tools()` — previously a
  tool removed from `tdmcp/tools/` left an orphaned row behind forever (still
  listed in the admin UI, still assignable via `Role.allowed_tools`). Safe to
  do unconditionally because the built-in server's tool rows have no
  admin-editable fields to lose — the built-in MCP detail page is read-only,
  informational only.

- Removed the `get_query_examples` MCP tool entirely (it demonstrated the new
  auto-pruning from the previous entry: its `ToolConfiguration` row
  disappeared from the admin DB on the next `migrate` with no manual
  cleanup). Deleted `tdmcp/tools/get_query_examples.py` and its registration;
  removed the now-fully-dead `QueryExample` parsing machinery it was the only
  caller of (`markdown_parser.py`'s `QueryExample` dataclass,
  `_parse_query_examples()`, `_examples_cache`, and the `get_query_examples()`
  parser method — `search_docs` remains fully able to find the same markdown
  content generically). Removed every other mention: the `_CHART_EDIT_TOOLS`
  allowlist, `builtin_mcp.py`'s `TOOL_CATEGORIES`, `query_database`'s
  docstring ("ALWAYS call get_query_examples first..."), the Tether-graph and
  Doc-generation system prompts, the default Codex/Claude agent system
  prompts (`containers/*/{AGENTS,CLAUDE}.md`), and this repo's own
  `CLAUDE.md` architecture list. Left the unrelated `query_examples`
  *documentation-generation type* (`DOC_TEMPLATES["query_examples"]` in
  `engine/prompts/docs.py`, used by Generate Documentation's Type field)
  alone — it's an independent, still-functional feature (AI-authored SQL
  cookbook pages, still fully searchable via `search_docs`), not the tool.

- Built-in MCP server tool cards now show each tool's real parameters (type
  badge, then name) and return type, below the description. Optional
  parameters' name renders in the Docs tab's lime accent instead of the
  default red.
  `Tool.from_function(handler)` — the exact schema FastMCP builds when
  registering the tool for the agent — via a new `describe_tool_schema()` in
  `tdmcp/tools/__init__.py` and `describe_builtin_tool_schemas()` in
  `engine/builtin_mcp.py`, wired into the admin `tools` API action. Not
  persisted to the DB (unlike name/category/description): it's cheap to
  recompute per-request and there's no admin-editable field to preserve.
  Custom (non-built-in) servers have no local Python function to introspect,
  so their tool cards are unaffected — `parameters`/`returns` are simply
  omitted from the API response for those. New `ToolSchema` component and
  `.tool-schema*` CSS in `MCPServerDetailPage.tsx`/`layouts.css`; also
  switched `.choice-card--static` to top-aligned icons, since these cards can
  now grow tall with a parameter list instead of staying single-line like
  the clickable option-picker cards this variant borrows its look from.

## Fixed
- The built-in MCP server's detail page rendered its **Back** button below
  the description text instead of top-right next to the title, unlike the
  custom-server detail view. Cause: `.page-header`'s title/description block
  had no `flex-basis`, so it defaulted to sizing itself by its *unwrapped*
  text width for the purposes of `flex-wrap` line-breaking — the built-in
  server's long description (~180 characters) overflowed the row on its own,
  pushing the button group onto its own line below. Fixed by giving
  `.page-header`'s first child `flex: 1 1 0%; min-width: 0`, so it's sized
  from 0 and grows/wraps to fill the remaining row space instead, matching
  the layout on every other `.page-header` (Add Codebase, Add Database
  Connection, custom MCP server detail, etc.).
- The built-in MCP server's description (shown on the MCP Servers admin
  list and the Tools & Prompts page) still read "…Served in-process by the
  MCP container; always active and cannot be edited or deleted." on
  existing installs, even though `BUILTIN_SERVER_DESCRIPTION` in
  `engine/builtin_mcp.py` had already dropped that sentence. Cause:
  `ensure_builtin_mcp()` only wrote `name`/`description` on first create,
  never on re-sync (unlike the tool rows, which already use
  `update_or_create`), so an install whose row was seeded before that
  wording change stayed stuck with the old text through every later
  `migrate`. `ensure_builtin_mcp()` now re-syncs `name`/`description` to
  the current constants whenever they drift, self-healing on the next
  `migrate` like the tool rows already do.
